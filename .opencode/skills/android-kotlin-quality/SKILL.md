# Качество Android/Kotlin

## Перед изменениями
Прочитай AGENTS.md и фактические конфигурации Gradle/version catalog. Сохраняй существующие соглашения. Не подставляй версии зависимостей по памяти и не добавляй библиотеку, если достаточно существующего стека.
Предложи небольшой diff и критерии проверки. Не строй многомодульную Clean Architecture для простого MVP без необходимости.

## Kotlin
- Предпочитай val, явное моделирование состояний и null safety; избегай !! без доказанного инварианта.
- Не используй Any, unchecked cast, глобальное изменяемое состояние и пустые catch как обход типов/ошибок.
- Ошибки представляй понятно пользователю, диагностическую причину сохраняй без персональных данных.
- Используй ограниченные области корутин. Не используй GlobalScope.
- Не проглатывай CancellationException; при широком catch сохраняй отмену.
- Делай блокирующие операции main-safe; IO dispatcher — для блокирующего IO, CPU/native inference — для подходящего ограниченного executor/dispatcher.
- Не предполагай, что suspend автоматически делает JNI-вызов неблокирующим или отменяемым.

## Compose и lifecycle
- UI отображает state и отправляет события; business logic не помещай в composable.
- Используй ViewModel для состояния экрана, где это оправдано, StateFlow/Flow и lifecycle-aware сбор согласно существующим зависимостям.
- Побочные эффекты выполняй в подходящих effect API, не в теле композиции.
- Не храни Activity/Composable/короткоживущий Context в долгоживущих объектах.
- Смена конфигурации не должна незаметно перезапускать запись или генерацию.

## LLM/STT и JNI
- Не блокируй UI загрузкой GGUF, STT, inference и индексацией.
- Явно моделируй unloaded/loading/ready/running/error, исключай гонки load/generate/release.
- Не вызывай один native context конкурентно без подтверждённой потокобезопасности.
- У каждого native handle должен быть владелец; release — идемпотентный и безопасный относительно активной задачи.
- Отмена требует кооперативного сигнала в runtime; отмена Job не равна остановке native inference.
- Проверяй формат/доступность/размер импортированного файла; большие файлы не читай целиком в ByteArray.
- Не используй большие веса в assets по умолчанию. Импортируй/загружай в согласованное хранилище, учитывая URI и доступ к файлу.
- При раннем arm64-only runtime честно помечай ограничения x86_64-эмулятора; UI можно проверять с fake backend. Не менять ABI без согласования.

## Данные и календарь
- Разрешения запрашивай при действии пользователя; обработай отказ.
- Сохраняй исходный текст транскрипции отдельно от интерпретации, если это нужно UX.
- JSON/tool-call валидируй приложением; ограничивай список инструментов. Не выполняй произвольный SQL от модели.
- Используй параметризованные запросы, транзакции и версионирование схемы.
- Даты: явная timezone, проверки интервала и уточнение неоднозначности.
- Не повторяй запись события при retry: предусматривай защиту от дублей.
- RAG-ответ должен ссылаться на найденные источники; при отсутствии данных не выдумывать ответ.

## Проверки
Используй Wrapper и фактические задачи проекта; команды PowerShell приведены в AGENTS.md.
Проверь assembleDebug, unit-тесты и lintDebug для релевантных изменений, либо явно объясни пропуск.
Добавляй focused-тесты: ошибки/отмена, валидация tool-call, даты/timezone, отсутствие результатов поиска и отказ в разрешениях.
Для корутин предпочитай детерминированные тесты с test dispatcher, а не Thread.sleep.
Нативную производительность, память, микрофон и календарь проверяй на физическом устройстве; не подменяй это успешной сборкой.
